# 加载失败：复现、修复与实际验收

日期：2026-09-06（UTC）。本次由用户实际报告触发，原先的软件测试通过没有覆盖交付后预览进程仍在运行这一条件。

## 已确认的原因

`127.0.0.1:8918` 当时没有监听进程，直接健康请求得到 connection refused。用户已加载的页面显示“加载失败 / Failed to fetch”，顶部却仍保留 `live · 745 posts`。前者来自停止的预览服务，后者来自页面只在首次启动时更新连接标志的缺陷。没有退出日志可以确定旧进程何时、为何退出，因此不把原因归咎于账户额度、用户升级或浏览器本身。

## 修复

- 新增根目录 `Start Preview.cmd` 与 `server/start-preview.mjs`。使用项目已有 Node 运行环境，隐藏启动独立进程，先确认健康再报告成功；重复运行只复用同一工作副本的健康预览。日志及上次启动记录放入被忽略的 `server/.preview/`。
- 预览响应包含工作副本的不可逆路径摘要与进程 ID，健康检查禁止重定向，避免复用另一程序或另一端口。占用、无响应或不健康端口明确失败，不杀掉其他进程。检查健康前后和记录启动后再次查看已观察到的子进程退出状态。
- 页面改为“最近请求成功”，请求失败后更新为断线或异常，提供主动重试，完整 JSON 请求限时 15 秒。不会自动重发评分或修订。完整实现范围见 [连接恢复验收](connection-recovery-2026-09-06.md)。
- Windows 最初拒绝执行 PowerShell 脚本；该未采用的脚本已移除，最终入口直接使用 Node，没有更改系统执行策略。后台进程采用 Node 官方支持的独立子进程、关闭父端日志句柄及取消父进程等待机制，见 [Node 子进程说明](https://nodejs.org/api/child_process.html#optionsdetached)。

## 本机实际验收

| 场景 | 实际结果 |
|---|---|
| 启动命令结束后 | 新预览仍监听 8918；已确认启动父进程退出 |
| 重复启动 | 返回同一 PID 和 `already-running`，不再启动另一份服务 |
| 原用户页面 | 恢复服务并刷新后，成功显示失实陈述首页 |
| 真实停服后切换页面 | 显示“连接已中断”、明确原因和“重试加载”；不继续显示绿色 live |
| 首次资料请求失败 → 重试 | 独立浏览器测试页通过本地故障代理中断 API，显示“暂时无法读取资料”；恢复代理并点击“重试连接并加载”后显示要件首页，无需重载页面 |
| 后续导航失败 → 重试 | 同一测试页打开 API/MCP 时中断请求，出现加载失败；恢复代理并点击“重试加载”，显示 REST 端点和 MCP tools |
| 成功后隐藏连接按钮 | 实际 DOM 为 `hidden=true` 且可见矩形数为 0，修复 `.chip` 样式覆盖原生隐藏规则的问题 |

后两项恢复检查采用独立测试页和仅监听本机的临时代理，正常 8918 服务保持运行。临时测试页已关闭、代理进程已停止。用户预览保留；未操作原有 8899/8901 服务。

根代理最终执行 **243/243 Node 测试通过**：原 214 项、5 项真实临时预览进程测试、24 项连接恢复测试。日志位于本地 `.git/codex-review/2026-09-06-connection/server-tests-final.txt`。另一个代理在 Node 24.19.0 下得到相同结果。

## 仍需说明的范围

这仍是本地预览。电脑重启或进程被关闭后须重新启动；网页本身不能启动操作系统进程。后台启动不等于部署为持续可用服务，也不是崩溃自动重启机制。重复启动复用进程，不会重载已导入的服务器代码。
